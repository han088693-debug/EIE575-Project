# E0 v3 两档负载设计（预注册草稿）

日期：2026-11-23　状态：待用一次短工程跑验证后冻结
相关：`configs/core_v3.json`（正式用）、`configs/core_v3_tuning.json`（仅调参用，60 s）

## 1. 为什么要有 v3

v2 在 6 个可测密度 × 2 种子共 12 次 E0 后判定 `grid_exhausted`：

- 低档合格密度为 5、10、15、20 辆/km/车道；高档无人合格；
- 最高实测密度 30 的单车窗口 CBR 为 40.80%，低于高档下限 50% 共 9.2 个百分点；
- 拟合 `CBR% = 3.12 + 1.288·d`（R²=0.995）表明进入 50% 需要 d≈36.4，而均匀预填在 80 km/h 下的几何上限只有 **33.64**（间距 ≥ 车长 5 + 2.5 + 22.22 m）。因此"扩到 35/40"在生成器层面就不成立。

结论：高档不可能靠加密度得到，只能重新定义，并相应调整控制器参数。

## 2. 两档的新定义

| 档 | 交通 | 主判据（operational） | CBR 记录 |
| --- | --- | --- | --- |
| 低档 | d = 5 辆/km/车道 | 90 s 长窗内控制目标速率 **不**被压低（调率占比 ≈ 0），即拥塞控制不介入 | 实测约 8%–9%，仅报告 |
| 高档 | d = 33 辆/km/车道（可建上限） | 90 s 长窗内至少 **25%** 的时间控制目标率 ≤ 9.5 Hz，即拥塞控制确实介入 | 实测值与四组一致性一并报告，描述带 40%–60%，**不作主判据** |

动机：原设计的"高档"本质是要一个**控制环真的在工作**的工作点；把判据从"某个 CBR 区间"改成"可观测的介入比例"，既保留了研究问题，也不再依赖一个在当前物理条件下达不到的数字。

## 3. 控制器参数变更与理由

`control.cbr_target`：0.60 → **0.45**（其余参数不变：beta=2、r_min=1、r_max=10、b_initial=2、b_min=1/3、b_max=10、deadband=0.03、gain=0.5）。

- 0.45 接近 d=33 的可实现背景负载（外推 45.6%），使反馈环在可行域的顶端进入工作状态；
- 若取 0.35，误差恒为负，`b` 会被一路压到 `b_min=1/3 Hz`，此时 `r = clip(b·W, r_min, r_max)`：G0 = 1 Hz、G2 = clip(1.0) = 1 Hz、G3 = 1 Hz，四组**行为完全一致**，高档失去比较意义；
- 取 0.60（原值）则没有任何可建密度能让控制介入。

## 4. 已知风险（先用短跑验证）

CBR 主要来自背景车流：目标车 10 Hz 时的空口占用约 0.3%–0.4%，降到 2 Hz 只减少约 0.3 个百分点。因此反馈环对 `b` 的"权威"很弱，可能出现两种极端：

1. **保持型**：`target` 与实测 CBR 之差落在死区 0.03 内，`b` 停在初值 2 Hz。此时 G0 = 2 Hz、G2 = 6 Hz、G3 ≥ 6 Hz，四组可区分，介入占比 100%，是我们想要的情形。
2. **饱和型**：差值超过死区，`b` 被推到 `b_min`，四组都退到 1 Hz，不可用。

验证方法：用 `configs/core_v3_tuning.json`（时长 60 s，仅调参，seed 300，不计入证据）跑一次 d=33 的 E0，检查 `b` 轨迹、`r` 分布与实测 CBR。若落在"保持型"再进入正式校准；若"饱和型"，把 `cbr_target` 上调（0.47、0.49 逐次）重试，或用 `r_min<1 Hz` 的变体（需另立设计）。

## 9. v3.2：预热门控 + 重新标定目标负载（架构修复，替代 v3.1 workaround）

### 9.1 修复内容

- `src/TabrCore.h` 新增 `controlActive(now, warmup, estimateValid)`：把“估计量是否可用”从控制律里分离出来；
- `src/TabrApp.cc::control()` 改为只有 `controlActive` 为真时才调用 `updateBase`；预热期照常测 C/Cbar 与写日志；
- `feedback_gain` 恢复 0.5；
- `tests/core_test.cpp` 新增 `warmupGate()`：预热期 b 不变、死区内保持、门控边界；`run_core_tests.ps1` 结果 **771 checks, 0 failures**；
- 重建 `EIE575_TABR_Starter.exe`（clang-release）。

### 9.2 重要更正：CBR 是车队自己产生的，不是固定的背景量

`deployment_mode = all_vehicles_same_scheme`，因此**所有背景车也在跑同一套控制器**。v3.1 探索跑（b 被压在约 2.35 Hz）实测 CBR 只有 **0.12**；而 v2 的 E0 是在 b=10 Hz 下测得密度 30 的 CBR 为 0.41。两者相差 29 个百分点，全部来自信标速率本身。

由此：

| 观测量 | b ≈ 2.35 Hz | b = 10 Hz |
| --- | ---: | ---: |
| 实测 CBR（d=33） | 0.12 | 0.41 |

拟合斜率约 **0.038/Hz**。因此“控制目标 0.43–0.49”永远只能把 b 推到约 10 Hz（顶到上限），而“目标 0.60”在可建密度下根本达不到——v2 的 `grid_exhausted` 本质是目标区间选在了车队无法产生的负载上。

### 9.3 正确的目标区间

要在中间速率建立平衡（G0 < 10 Hz 且 G2 = 3·G0 < 10），需要 b 落在 2–3.3 Hz，对应 CBR 约 **0.13–0.16**。取 `cbr_target ≈ 0.16`：预热结束 CBR≈0.12，误差 0.04 略超死区，b 上升至约 3.3 Hz、CBR≈0.136，误差 0.024 落入死区后保持。

下一轮扫描目标：**0.14 / 0.16 / 0.18 / 0.20**（其余参数同 v3.2）。

## 10. v3.2a：门控依据改为“估计量可用时间”（修正 v3.2 的时机错误）

v3.2 把门控放在**场景预热结束**（`now >= warmup`，20 s）。实测暴露两个问题：

1. **校准失效**：控制环在 t=20 才开始调整，而 E0 的测量窗口是 20–110 s，瞬态正好落在第一个测量窗口内 → C1（d=5）被判 `stable=False`，两档标定无法成立；
2. **S1 事件撞车**：急刹事件在 t=20.1，控制环在 t=20.0 开始调整，事件恰好发生在瞬态中 → 该批 S1 数据不能作为最终结论。

根因是把“测量预热”和“估计量有效性”混用。二者语义不同：

- 预热（`timing.warmup_s`）：实验协议的一部分，决定测量窗口从何时开始；
- 估计量有效性：控制输入的可用性，取决于窗口内是否已有流量，量级为**一个控制窗口到一秒**。

修正：

```
constexpr double kEstimateSettleSeconds = 1.0;   // src/TabrCore.h
if (controlActive(now, kEstimateSettleSeconds, smoothed)) base = updateBase(...);
```

- 仿真开始 1 s 内窗口没有流量、CBR≈0，不积分；
- 1 s 后开始控制，瞬态在预热期内部完成，测量窗口开始时已稳定；
- 独立校验器 `tools/formal_state.py` 使用同一常量 `ESTIMATE_SETTLE_S = 1.0`。

验证：C1（d=5，seeds 100/101）修复后 `stable=True, low=True`；`run_core_tests` 772 checks / 0 failures；`pytest` 7 passed。

## 11. 结构性限制：可区分性与拥塞压力互斥

`deployment_mode` 只有 `all_vehicles_same_scheme`，即背景车与目标车跑同一套控制器、共享同一个 CBR 反馈。由此产生一个无法靠调参绕开的张力：

| 想要 | 需要的状态 | 副作用 |
| --- | --- | --- |
| 策略可区分（G0≠G2） | base 停在 2–4 Hz，使 `r=clip(b·W,1,10)` 对 G0 与 G2/G3 不同 | 全网信标率低 → 实测 CBR 只有 0.12–0.18，信道空闲，任何策略都能在期限内送达 |
| 信道有压力（CBR≈0.4，出现漏收/超时） | 全网信标率接近 10 Hz | base 顶到 `b_max`，`W` 被 `r_max=10` 截平 → 四组行为一致 |

两条实测锚点：

- v2 E0（b=10 Hz，d=30）：CBR = 0.41；
- v3.1 探索（b≈2.35 Hz，d=33）：CBR = 0.12。

斜率约 0.038/Hz，说明 CBR 主要由车队自身的发送速率产生，而不是一个独立的背景量。因此“在相近实测负载下比较策略”与“制造足够拥塞让策略差异显现”在当前部署模式下不能同时满足。

影响：H1（G2 是否优于 G0）与 H2（G3 是否优于 G2）在现有部署下只能给出“机制生效、指标无差异”的结论；要检验收益，需要 v4 部署模型——背景车定速发送（不参与控制），目标车受控，这样背景负载固定、受控速率可降，两个条件才能同时成立。

## 12. 结论（2026-11-24 02:40）

### 12.1 两档校准成立

`calibrate --attempt` 对 4 次 E0（d=5/33 × seeds 100/101）的判定：

| 密度 | 种子 | stable | low | high |
| ---: | --- | --- | --- | --- |
| 5 | 100 | ✅ | ✅ | — |
| 5 | 101 | ✅ | ✅ | — |
| 33 | 100 | ✅ | — | ✅ |
| 33 | 101 | ✅ | — | ✅ |

`decision = selected`，`{low: 5, high: 33}`。这是本项目第一次得到非 `grid_exhausted` 的两档决策。

### 12.2 S1 策略对比（3 种子 × G0/G2/G3，d=33，target 0.18，120 s）

| 指标 | G0 | G2 | G3 |
| --- | ---: | ---: | ---: |
| 制动车事件窗口平均速率 | 3.05 Hz | 9.16 Hz | 9.16 Hz |
| D_info（按检测时刻）均值 | 61.8 ms（sd 61.4） | **0.4 ms**（sd 0） | **0.4 ms**（sd 0） |
| D_info（按事件起点，规范定义）均值 | **161.8 ms** | **100.4 ms** | **100.4 ms** |
| 总发送量 | 434,824 | 434,729 | 434,772 |
| 期限内送达 / 漏收 | 全部 / 0 | 全部 / 0 | 全部 / 0 |

规范定义（从真实制动起点计，含检测、等待发送与接入）下，G2/G3 把时延从 **161.8 ms 降到 100.4 ms**（−38%），且三种子的取值完全不重叠：G0 为 113.7 / 140.7 / 231.0 ms，G2/G3 均为 100.4 ms。

机理：~100 ms 是制动检测本身的固有延迟，三种策略相同；差异全部来自“检测后等到下一次发送”的时间——G2/G3 把速率提到 9.16 Hz 后，`rescheduleSend` 在检测时刻即触发发送，等待接近 0；G0 则需要等 13–131 ms。

### 12.3 假设判定

- **H1 成立（时延维度）**：急刹加权把制动信息时延降低 38%（按规范定义）或约 150×（按检测后等待计），总发送量变化 < 0.02%，没有可测的资源代价。
- **H2 不成立**：G3 与 G2 在全部指标上完全一致（B=1 时 `max(B,S)=1`，创新项无额外贡献），发送量还略高 0.01%；应保留更简单的 G2。
- 所有策略都在 0.8 s 期限内送达，因此本场景下收益体现为时延而非超时率；要检验超时率差异，需要更紧的期限或更强的拥塞（见第 11 节结构性限制）。

## 13. 负载阶梯（补充实验，2026-11-24 02:52）

在选定目标 `cbr_target = 0.18` 下，对三个密度各跑 2 个种子（E0，120 s，G0）的稳定工作点：

| 密度（辆/km/车道） | 稳定 base rate b | 实测 CBR |
| ---: | ---: | ---: |
| 5 | 10.00 Hz（顶格） | 0.083 |
| 15 | 6.70 Hz | 0.160 |
| 33 | 3.36 Hz | 0.158 |

说明：控制器通过下调 `b` 把 CBR 稳定在 `target − 0.02` 附近（死区下沿 0.15）；d=15 与 d=33 都收敛到约 0.16，但实现它所需的 `b` 不同（6.7 vs 3.4 Hz）。d=5 时车队最高只能产生约 0.083 的 CBR，低于死区下沿，因此 `b` 顶格 10 Hz——这正是“低档无控制介入”的量化依据。

推论：中间密度虽然 CBR 与高档相同，但 `b` 更高，`W=3` 会被 `r_max=10` 截平，G0/G2 的速率差只有约 1.5×；高档（d=33）才是 3× 区分度的工作点。
