# 本地 git 工作约定

本文件是本仓库（`E:\Temp\eie575_tabr`）的操作准则。改动本文件同样需要走分支 + 提交。

## 1. 仓库定位

- 这是**工作仓**：代码、配置、文档、校准判定与测量入库。
- 大体积运行产物不入库：`results/probes/`、`out/`、`*.exe`、`__pycache__/`、`verification/wall_runtime/`（见 `.gitignore`）。
- 交付与发布走另一个仓库（GitHub `han088693-debug/EIE575-Project`），两者互不推送。

## 2. 分支规则

- 主题分支一律以 `sh/` 开头：`sh/<主题>`，主题用短横线连接的小写英文，例如：
  - `sh/e0-v3-two-tier`
  - `sh/t0-sweep-configs`
  - `sh/e0-v31-slow-feedback`
  - `sh/workflow-convention`
- **一个分支只做一件事**。发现第二件事，就从当前提交切新分支，不在原分支上混做。
- 新分支从它所依赖的最新提交切出（通常是上一个主题分支的 tip，或 `main`）。
- `main` 只放已确认收敛的内容；不在 `main` 上直接开发。

## 3. 提交规则

- **一次最小改动 = 一个提交**。以下情况必须拆开：
  - 改代码 与 改配置；
  - 改参数 与 补文档（除非文档就是在解释这次参数变更）；
  - 两个互不相关的修复。
- 提交信息：第一行祈使句、不超过 72 字符，说明“做了什么”；需要时正文写“为什么”。
  - 好的：`Raise wall budgets: 2 h for tuning probes, 4 h for 120 s runs`
  - 不好的：`update`、`fix`、`misc changes`
- 不使用 `--amend` 重写已汇报过的提交；需要修正就再提交一次（历史要能看出演化）。
- 提交前必须：`git status` 干净、配置改动用 `experiment.py validate` 过一遍、能跑自检就跑。

## 4. 合并规则

- 主题分支完成并通过自检后，向负责人汇报，**由负责人决定**是否合并进 `main`。
- 合并用快进（`git merge --ff-only`）；不做无人确认的强推或历史重写。
- 合并后该分支可删除；历史保留在 `main` 中。

## 5. 与运行的关系

- 仿真进行中允许提交代码与配置，但不得改动正在使用的运行目录（`results/`、attempt 目录）。
- 改动控制参数或场景时，必须同时更新对应设计文档（例如 `docs/E0_v3_两档设计_20261123.md`），并在提交信息里点明是设计修订。
- 任何一次“参数改动”都要能回答：改的是哪个字段、旧值、新值、为什么、影响哪批数据。

## 6. Bug 修复：架构层改正，不打补丁

看到缺陷时，先定位根因，再在架构层（数据流、状态机、接口契约、不变量）改正；**不以调参数掩盖症状作为最终修复**。

| 症状 | 禁止当作修复（补丁） | 架构改正 |
| --- | --- | --- |
| 控制器预热期冲顶 | 把反馈增益调小 | 估计量未有效前不进入控制（显式有效性状态 + 预热门控） |
| 偶发超时 | 把墙钟一味调大 | 预算来自实测基准，配进展检测与授权续期 |
| 字段缺失导致崩溃 | 加 try/except 吞掉 | 明确接口契约与必填校验 |

每个修复提交必须写清三件事：

1. **根因**（一句话，能指向具体代码位置）；
2. **为什么不打补丁**（补丁会掩盖什么、会引入什么偏差）；
3. **防回归**（新增/修改的测试；确实无法加测试时说明理由）。

### 运行阻塞时的例外协议

缺陷挡住正在进行的实验、且短期无法完成架构改正时，允许临时绕行，但必须：

- 独立分支，提交信息以 `workaround:` 开头，并在设计文档登记为技术债；
- 写明移除条件与对应架构修复分支名；
- `workaround` 提交**不合并进 `main`**，只用于让实验继续；
- 架构修复落地后，重新用正式口径复跑受影响的数据，旧结果标注为“基于绕行方案，仅作探索”。
